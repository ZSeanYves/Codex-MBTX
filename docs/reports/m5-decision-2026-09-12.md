# M5 Codex-MBTX 决策报告（2026-09-12）

## 1. 执行摘要

本报告回答的问题是：**在 Codex 中，Transparent MBTX 是否已经有足够证据替换现有 Shell，并成为默认后端？**

最终分类为 **`INCONCLUSIVE`**，部署建议为 **保持 `opt-in`，暂不设为默认**。这不是对 MBTX 的否定，也不是把中转故障算作后端回归，而是正式 formal cohort 没有完成：pilot 和 formal W1 有效，W2 在三次有证据的中转尝试中均未得到可用窗口，因此 W3 没有合法的完整前缀可接续。

当前证据能支持的最强结论是：

- **MBTX 自身事实**：Linux x86_64 与 Darwin arm64 的确定性运行时、退出/取消/回收、固定轨迹回放均未发现语义或子进程清理回归；B2 bare-proxy 的额外开销通常是毫秒级。
- **Codex adapter 事实**：approval 仍展示原始命令，Transparent launcher 只在最终启动阶段加入；固定回放的 argv、cwd、sandbox、输出、退出码、事件顺序和清理结果与 Shell 一致。
- **模型/任务事实**：W1 的少量失败集中在 `host_stdin_stream` 和一次 `host_literal_argv` 的精确命令契约，且两臂都出现；它们不能被解释成 MBTX 的确定性语义失败。
- **relay 事实**：W2 出现一次 probe transport disconnect、一次通过 probe 但正式 batch 大面积 403/断流、一次 10/10 403 provider error。它们被保留为基础设施无效样本，没有进入 backend 优劣结论。
- **尚不能声称**：Transparent 的完整 formal 成功率、p95 优势或劣势，生产成本优势，以及 Windows 兼容性。

因此，本轮不能给出 `GO_DEFAULT`、`OPT_IN_ONLY` 或 `NO_GO` 作为统计分类；按预注册规则只能是 `INCONCLUSIVE`。在产品动作层面，最稳妥的建议是继续提供 Transparent MBTX 的显式 opt-in，同时不改变 Codex 的默认 Shell 路径。

## 2. 研究对象与因果边界

运行臂固定为：

| 臂 | 定义 | 能回答的问题 |
| --- | --- | --- |
| B0 `shell` | Codex 现有 Shell 路径 | 基线端到端行为 |
| B1 `transparent` | 当前真实 Transparent 配置，adapter 在最终启动阶段走 Direct shell 路径 | 是否值得替换 Shell |
| B2 `bare-proxy` | 脱离 Codex 与模型，直接运行 `mbtx exec --` wrapper | wrapper 自身开销和生命周期事实 |

B0/B1 才是默认后端决策的主比较。B2 不能被当作 Codex 端到端结果。显式 `mbtx` 工具和 MoonBit 脚本生成属于独立 `script-capability` cohort；本轮没有把它们混入 Shell 替换结论。

在线主平台是 Linux；macOS 只用于确定性运行时和回放对照；没有 Windows 结论。在线冻结变量为 implementation SHA `cbff45de17edb675a3042146a4c231ac81abfcc4`、model `gpt-5.6-terra`、reasoning effort `xhigh`、seed `20260910`、tool catalog `apply_patch,exec_command,view_image,write_stdin`，以及报告中记录的 Codex/MBTX/runner/evaluator hash。

## 4. Relay 健康、重试和无效样本

### 有效 probe

- pilot：10/10 成功，provider/transport error 均为 0，first-byte p95 `2613 ms`。
- W1：10/10 成功，provider/transport error 均为 0，first-byte p95 `1836 ms`。

### W2 三次中转尝试

1. **retry 1（34651280446）**：10 个 probe 仅 9 个成功，`probe-6` 为 `stream_disconnected=true`、`transport_error=true`；first-byte p95 `59264 ms`，超过 15 秒门槛。没有新增可接受 block。
2. **retry 2（34652337987）**：probe 本身 10/10、p95 `2295 ms`，但正式 batch 的 112 个 run 只有 18 个 relay-clean，79 个 run 为 provider error、15 个为 transport error；Shell/Transparent 基础设施失败分别为 46/56 与 48/56，差异约 3.57 个百分点，超过 2 个百分点门槛。总 attempt 723，retry attempt 79，恢复 2 次，重试额外 elapsed `121784 ms`。这批必须整体作废，不能从其中挑出看起来较快的配对。
3. **retry 3（34661904479）**：10/10 probe 均为 HTTP `403` provider error，连续失败 10，成功数为 0。没有新增可接受 block。

上述证据足以把 W2 失败归因到 relay/provider 可用性，而不是归因到某个 backend。重试次数达到本轮约定上限后停止；继续重复只会增加无效网络样本，不会提高因果证据质量。所有 provider/transport attempt、missing usage 和 `backend_observation=unknown` 都被保留在原始报告或 probe artifact 中，没有改写成 backend violation。

## 5. 确定性运行时（B0 vs B2）

pilot 同时冻结并验证了两平台 artifact：Linux x86_64 和 Darwin arm64 各 `21600` 条样本，共 `43200` 条。每个平台包含 9 个场景、Shell/bare-proxy 两臂、200 次 cold 和 1000 次 warm 样本；外部 harness 使用单调时钟，child 输出开始/结束 marker，因此 wrapper overhead 没有被误当成 child execution time。

两平台均满足：

- 内容、argv/cwd、stdin/UTF-8 和 stdout/stderr 校验无意外失败；
- child start marker 缺失为 0；
- 子进程清理失败为 0；
- `stop`、`timeout`、`cancel` 的 7200 条/平台缺少 child end marker 是预期的主动终止结果，不是错误；
- `large-output` 每平台 2400 条 stdout 不完整是预注册的输出上限行为，其余流完整性没有意外失败。

`runtime-*-summary.json` 保存全部摘要，压缩原始样本为 `runtime-linux.json.gz` 和 `runtime-darwin.json.gz`。B2 相对 B0 的配对差异如下；这些是 wrapper 测量，不是 B1 的 Codex 端到端延迟：

| 平台 | workload | cold delta p50 / p95 / p99 | warm delta p50 / p95 / p99 | 解释 |
| --- | --- | --- | --- | --- |
| Linux | argv、stdin、cwd、输出、nonzero | `+3--4 / +5--7 / +7--8 ms` | `+3 / +6--7 / +8 ms` | 稳定的毫秒级 wrapper 成本 |
| Linux | background、stop、timeout、cancel | `+2--4 / +7--8 / +8--10 ms` | `+1--4 / +6--7 / +8--10 ms` | 生命周期尾部仍为毫秒级 |
| Darwin | 普通场景 | `+3--4 / +14--20 / +16--38 ms` | `+3 / +6--9 / +10--15 ms` | 调度尾部比 Linux 更宽 |
| Darwin | 生命周期场景 | `-1--+4 / +27--63 / +36--87 ms` | `+2--3 / +24--131 / +35--151 ms` | background 调度尾部需单独关注 |

因此，当前能说的是“MBTX wrapper 可工作且通常只带小额固定开销”；不能把这个结果外推成 Transparent 一定更快。尤其 Darwin 生命周期尾部和 Codex B1 的模型/relay 时间必须分开测量。

## 6. 固定轨迹回放（B0 vs B1）

Linux、Darwin 各自保存 10 条固定轨迹、3 次重复，即每个平台 30 条 trajectory、60 个 backend run。回放覆盖 literal argv、stdin、cwd/environment、输出顺序和大输出、非零退出、background/poll、cancel、timeout。

结果：

- paired semantic mismatches：`0`；
- paired trace mismatches：`0`；
- semantic failures：`0`；
- 子进程清理失败：`0`；
- Transparent launcher 缺失：`0`；
- Shell 错误加入 launcher：`0`。

回放还验证了 approval 原始命令、解析后的 argv、sandbox/cwd、workspace diff、退出码和事件顺序。Transparent 记录包含 `launcher_start`/`launcher_exit`，Shell 记录不包含 launcher。回放是脱离 relay 的 adapter-contract 证据，不冒充真实模型随机轨迹；Codex mock Responses/SSE 编排由既有 Rust 集成测试覆盖。

| --- | ---: | ---: | ---: |

pilot 明确显示可观测链路能跑通，但样本量只用于发现 fixture、oracle 和计时问题，不能宣布默认替换。

### 7.3 W1 任务级失败与 oracle 影响

| task | Shell | Transparent | 观察 |
| --- | ---: | ---: | --- |
| `host_literal_argv` | 6/7 | 7/7 | Shell 有一次精确 argv/cwd 失败 |
| `host_stdin_stream` | 4/7 | 2/7 | 两臂均出现模型命令契约偏差 |
| 其余 6 个任务 | 7/7 | 7/7 | 未见任务级失败 |

9 个失败 run 的历史 `failure_category` 都是复合标签 `workspace_dirty`，但逐字段检查显示：`workspace_clean=true`、输入保持、权限/符号链接保持、receipt 有效、子进程已清理，且流和退出码检查通过；真正共同的异常是 `argv_cwd_valid=false`，其中一次 literal argv 的输出也不正确。这个标签不能被当作“文件系统被污染”，也不能升级成 MBTX 安全回归。后续评测应把它拆成独立的 `command_contract_violation`，避免任务设计和 oracle 分类混淆。

## 8. Script capability cohort

本轮没有运行 MoonBit script cohort，符合“不要把脚本生成内容和 Shell 替换混合”的边界。历史 M4 explicit-tool 报告保留原样，但不提供 Transparent 替换 Shell 的证据。因而本报告不对显式 `mbtx` 工具或 MoonBit 脚本生成能力作收益结论。

## 9. 故障注入与证据管线

本地 mock relay 故障注入 `faults.json` 共 9/9 通过，覆盖：502、429/Retry-After 恢复、SSE 断流、malformed partial、慢首字节 gate、timeout/cancel race、output limit、malformed probe arm/window 和 unknown backend interruption。验证结果包括：`unknown` 保持 unknown、不转成 violation；失败 attempt、partial usage 和 retry 成本均能保留；runner 崩溃仍能保存 evidence。

本轮收口还修正了工作流中的两项可复现性问题：CI/M3 使用已验证的 MoonBit `0.10.12+1634b282e`，`moonbitlang/async` 为 `0.21.3`；health gate 失败的 continuation 保留原 runner hash，不再因暂时禁止 runner 而错误拒绝完整前缀。在线证据仍以测量时的 implementation SHA `cbff45d...` 为准；本报告和工作流文档的后续提交不应被误认为重新采集过在线样本。

## 10. 默认替换门槛

| 门槛 | 证据 | 结论 |
| --- | --- | --- |
| Linux/macOS 确定性语义零回归 | 两平台 43200 runtime 样本，内容/marker/清理无意外失败 | 通过 |
| approval、sandbox、argv、退出码、生命周期无安全/兼容回归 | 两平台固定回放 120 runs 零 mismatch；本地 Codex mock 集成测试通过 | 已覆盖部分通过 |
| 成功率单侧 95% 下界不低于 -2 pp | W1 为 -8.92 pp；完整 formal 未完成 | 未通过/不可定案 |
| p95 上界不增加超过 5% | W1 为 +48.68%；完整 formal 未完成 | 未通过/不可定案 |
| 没有关键任务确定性回归 | runtime/replay 无回归；W1 的 stdin/argv 是模型命令契约问题 | 通过（限定于已覆盖证据） |
| 证据完整率和 backend 可观测率达到预注册要求 | W1 前缀完整；W2 无有效窗口；W3 未运行 | 不通过 |
| 脱敏 artifact 可重建机器报告 | W1、pilot、probe、runtime/replay/fault artifact 可重建；完整 160 block 不可重建 | 前缀通过，正式结论不通过 |

所以最终状态是 **`INCONCLUSIVE`**，不是 `NO_GO`：没有发现确定性语义或安全兼容回归；也不是 `GO_DEFAULT`：缺少完整三窗口和足够窄的置信区间。由于预注册分类把“样本/健康不足”归为 `INCONCLUSIVE`，产品动作中的“opt-in”是保守部署建议，不是把统计状态改写成 `OPT_IN_ONLY`。

## 11. 给 Codex 团队的建议

1. 默认继续使用 Shell；Transparent MBTX 保持显式 opt-in，不宣传性能领先。
2. 先修 relay/认证层的 403 和断流来源，再重跑 W2/W3；不能用重试挑选最好看的 backend 分数。
3. 保留并使用 health gate、batch gate、ITT 和 relay-clean 双视图；无效窗口永远不进入 backend 比较。
4. 把 `workspace_dirty` 拆成文件系统差异、命令契约偏差、生命周期失败等互斥类别，并为 stdin/argv 任务增加更严格的模型轨迹 oracle。
5. 本轮已修复 continuation 在 health gate 失败时的 artifact 处理：保留 runner hash，`m5_eval` 仍不会调用 runner，并保存当前窗口的 invalid health artifact；下次重跑时从 W1 完整前缀开始。
6. 下次正式运行必须从 W1 完整前缀开始，完成 W2 56 blocks 和 W3 48 blocks；任何窗口失败都保留原始 artifact，不覆盖有效前缀。
7. 在有独立账单或可信价格数据前只报告 token，不从 token 直接推导费用。Windows、其他模型、其他 reasoning effort 和 script cohort 仍需独立实验。
