# M4 Evaluation: 2026-09-08

Status: the live retry reached both execution backends and exposed an evaluator

## Implementation and scope

M4 provides six fixed tasks, deterministic output checks, shell/MBTX routing
checks, token accounting, failure diagnostics and a manual GitHub Actions
workflow. Full mode runs each task twice per backend, for 24 rollouts. Every
rollout has a fresh workspace and Codex home, a 300-second deadline, and zero
human interventions under approval policy `never`.

The tasks cover JSON totals, invalid JSONL recovery, literal file paths and
UTF-8, literal argv, a small MoonBit repair, and background jobs with polling.
The installed toolchain and dependency cache are warm and shared. Backend
order alternates by task and repetition. The observed token guard is checked
after each rollout; it is not an absolute provider billing cap.

The tested runner and Codex binaries come from M3 commit
`8f1142da167970bb6c8deaee1b30c4ef0cdc4669`, whose relevant sources are compared
against the evaluator revision before reuse. The binary artifact is from
[M3 run 34187141796](https://github.com/ZSeanYves/Codex-MBTX/actions/runs/34187141796).
Codex is pinned to `rust-v0.153.4`, revision
`3d2ee51ca2d5db578f328aa75e20aa22c0197c9a`; MoonBit is pinned to
`0.10.11+6ff76a5f9`.

This pilot uses Direct tools. Terra's pinned catalog otherwise forces
JavaScript Code Mode, whose host is absent from the M3 two-binary archive.
The evaluator changes only the catalog's `tool_mode` to `direct`, equally
for both backends. Shell tools remain visible in the MBTX group; using them
is graded as a backend violation. This is an instruction-routed pilot, not
an adversarial grader or a validation of the Code Mode host.

## Retry and evaluator correction

[Run 34218788625](https://github.com/ZSeanYves/Codex-MBTX/actions/runs/34218788625)
used `gpt-5.6-terra / xhigh` at evaluator revision `b2b4257`. The immutable
[original artifact](m4-2026-09-08/34218788625.json) records:

- Shell completed in 254.076 s using six `exec_command` calls. Its retained
  `result.json` is exactly correct, inputs are preserved and routing is
  compliant. Seven of eight requests have usage; one provider error recovered.
- MBTX ran five scripts, all with model-generated syntax or import errors,
  then terminated after provider overload at 211.343 s. No result was written.
  Six of eight requests have usage. It used `mbtx` and `apply_patch` without
  shell fallback.

The controller incorrectly serialized `Option[String]`: a present file became
`[text]`, while the grader expected `text` or null. This falsely classified the
correct shell result as `incorrect_output`. The stored shell output was checked
against that run's suite using parsed JSON equality and passed. This is an
output-only correction of retained evidence, not a new paid rollout or a
reconstructed raw-event audit. The original artifact is unchanged. Historical
output-failure grades made by this controller are not valid model conclusions.

The controller now explicitly encodes a string or null, and the evidence CLI
rejects unexpected shapes. End-to-end CLI regressions cover correct content,
missing content and the old array wrapper. Prompt revision 2 gives both groups
the same MoonBit reference inline: previously MBTX had to guess the language
syntax just to read the reference file. Both workspaces also receive an empty
Git repository and ripgrep, addressing the observed shell environment errors.
These changes precede the formal comparison and are recorded in report schema 2.

The smoke also exposed a separate MBTX runner issue: MoonBit can print warning
records before the artifact JSON, while the runner previously parsed the whole
stdout as one JSON value. The runner now scans JSON lines, preserves diagnostic
records as stderr, and selects the artifact record. A regression test with an
unused variable passes after this fix. The full comparison must use a newly
built binary because the M3 archive predates this runtime change.

## Decision and next run

MBTX remains opt-in. The evidence currently supports the runner, adapter and
evaluation infrastructure checks, but does not establish a comparative
success rate, speed advantage or cost advantage for MBTX. A default-backend
change is not supported by these diagnostic attempts.

After a stable smoke succeeds, run the same model and reasoning configuration
for the complete comparison using the manual **M4 Evaluation** workflow.
Keep failed rollouts in the report and report missing usage explicitly.
The next smoke checks the corrected evaluator and inline reference against the
current relay. Persistent overload and incomplete streams still prevent a
reliable speed or token comparison. No additional local deployment or GPU is
required.
