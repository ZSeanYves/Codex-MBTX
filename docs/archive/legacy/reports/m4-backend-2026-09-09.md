# M4 Backend-Only Evaluation (2026-09-09)

This report records the process-only comparison for the transparent MBTX
backend. The workflow was
[34343213137](https://github.com/ZSeanYves/Codex-MBTX/actions/runs/34343213137)
at implementation commit `3d991e630138ea3350aabbcd3f937df35083b391`. It used
`gpt-5.6-terra` with `xhigh`, prompt revision 3, schema version 4, the pinned
MoonBit toolchain, and all 24 planned rollouts (six prewritten host-process
tasks, two repetitions, two backends). The live job failed its evidence gate,
but uploaded a complete 24-row report.

All 24 rows preserved their input files. There were no completed rows classified
as `backend_violation`; every completed `none` row used the normal
`exec_command` contract, and background rows also used `write_stdin`. No row in
this mode used the `mbtx` model-visible tool. `Correct output` is an independent
evidence field, so it can be true for a row that later timed out or lost usage;
`Passed` is the stricter `failure_category=none` count.

The apparent pass-rate difference is not a reliable backend advantage. Five of
the six shell failures were provider errors, while only one transparent row was
a provider error. The sanitized diagnostics repeatedly report
`Our servers are currently overloaded. Please try again later.` or a stream
disconnect. The failures are clustered by rollout position rather than evenly
paired across backends, so relay availability is confounded with backend order.
The two timeouts are also model/relay session failures, not MBTX runtime errors.

Only six task/repetition pairs completed with `none` on both backends. In that
selected subset the mean wall time was 137,639 ms for shell and 131,514 ms for
transparent. This is too small and too selectively observed to support a speed,
cost, or reliability claim. The full-cohort means include different provider
failures and different model trajectories, so they should not be read as a
launcher benchmark.

## What Was Actually Tested

The process cohort used already-written Python helpers for literal argv, stdin,
path inventory, background execution, bounded output, and nonzero-exit recovery.
The prompts did not ask the model to create, repair, or run a MoonBit file. The
same prompt and model-visible tools were supplied to shell and transparent
rows; only the local backend configuration changed. This is the correct cohort
for testing whether MBTX can replace the final process launch invisibly.

The earlier six-task cohort remains a separate **script** workload. Its
`capture.mbtx`, `broken.mbtx`, and `worker.mbtx` fixtures deliberately ask the
model to run or repair MoonBit scripts. Any `moon run` compilation in those
rows is part of the requested task and occurs under both backends. It is not a
hidden compilation performed by transparent MBTX.

## Causal Attribution

| Source | Evidence and conclusion |
| --- | --- |
| Test design | The old script tasks intentionally exercised MoonBit authoring and compilation. That makes them useful for a script-capability cohort, but unsuitable as the only transparent-backend benchmark. The new process cohort removes that confound. |
| Model and relay | The live report contains six provider errors and two timeouts, including repeated overload/stream-disconnect diagnostics. Completed rows also show model-level retries and expected command failures while tasks were being solved. These affect completion and wall time independently of the launcher. |
| Codex adapter | The adapter keeps `exec_command`/`write_stdin` visible, sends the original command through approval and sandbox planning, and adds the trusted launcher only after those checks. Local integration tests cover literal metacharacters, exit status, and approval visibility; remote M3 CI passed on the same commit. No adapter-only failure category appeared in the completed rows. |
| MBTX transparent runtime | `mbtx exec --` receives an already-resolved executable and argv, attaches stdin/stdout/stderr, waits for the child, and returns its exit code. It does not parse a shell command or enter the MoonBit script compiler. The isolated fixture check and the transparent integration tests passed. |
| MBTX explicit script design | The separate JSONL/script protocol necessarily compiles a supplied MoonBit source or `.mbtx` path before running it. That compile cost and API coupling are inherent to explicit script execution. They become a design mismatch only if the product tries to route every ordinary host command through that protocol. |

## Why MoonBit Knowledge Can Still Matter

There are two contracts that must not be conflated:

1. In explicit MBTX mode, the model calls the `mbtx` function and supplies
   MoonBit source or a `.mbtx` path. MBTX executes that program; it does not
   translate arbitrary natural-language work into MoonBit. The model therefore
   needs enough MoonBit syntax and API knowledge to produce a compilable script.
2. In transparent mode, the model sees the ordinary Codex execution tools. The
   adapter resolves the command, obtains approval, applies sandbox policy, and
   finally launches `mbtx exec -- <original argv>`. The model does not need to
   know that MBTX is present. It only needs MoonBit knowledge when the task
   itself asks it to edit or run a MoonBit fixture.

The phrase "every task generates, compiles, and executes a MoonBit script" is
therefore only true for explicit script requests or for a task that explicitly
invokes `moon run something.mbtx`. It is false for the transparent process path.
The evaluator's own `.mbtx` automation scripts are compiled to run the harness;
that harness compilation is separate from each model task.

## Implementation Evidence

- [`process/proxy.mbt`](../../process/proxy.mbt) documents that transparent
  execution receives literal argv, does not parse shell syntax, and does not
  compile generated MoonBit source. It attaches the caller's standard streams
  and waits for the child.
- [`cmd/mbtx/main.mbt`](../../cmd/mbtx/main.mbt) implements the separate
  `exec --` launcher and preserves the child's exit status.
- [`codex/integration.patch`](../../codex/integration.patch) keeps the launcher
  out of the command shown to approval/policy, then prefixes `exec --` only at
  final launch.
- [`core/tests/mbtx.rs`](../../codex/overlay/codex-rs/core/tests/mbtx.rs) covers
  the hidden explicit tool, literal arguments, nonzero exits, and approval of
  the original command.
- The local sanitized artifact is
  `_build/m4-remote-34343213137/report.json`; raw prompts and relay dumps were
  not published.

## Decision

This run validates the transparent execution contract and gives a useful
process-only baseline, but it does not establish that MBTX is faster, cheaper,
or more reliable than shell. Keep transparent MBTX opt-in while collecting
more stable relay runs with randomized paired order and enough repetitions.
Keep MoonBit authoring/compilation tasks as a separate capability cohort. If
the product goal is natural-language execution without MoonBit knowledge, the
transparent path is the appropriate contract; improving explicit script mode
requires separate model/API guidance, validation, and compilation caching.
